# F008 / F009 / F016 / F017（high）· 合并方案：RSI"自产证据 / 硬编码门禁分数"

> 状态：needs-design（同一根因，不在 fix-loop 内自动改——涉及"质量信号如何产生"的重设计 + god-module 拆分）
> 关联：[F001](F001.md)（门禁自批/覆盖人审）同属 game_production 自评信任问题

## 根因

KUN 的北极星是"RSI 真闭环"，而闭环的有效性取决于**喂给它的质量信号是否真实**。本组 4 项证明：当前多处"质量评分 / 门禁通过"是**硬编码常量或字符串指纹自检**，不是对产物的真实度量——RSI 在用伪造的信号训练自己。

| ID | 位置 | 事实（已核实） |
|----|------|----------------|
| F016 | `kun/control_plane/kun_runtime_runner.py:338-368` | `finalize_mission` 无条件构造 `GateEvaluation(north_star_verdict="pass", result_quality=0.82, speed=0.72, cost=0.78, risk=0.22, …, next_action="ready_to_deliver")`，分数全是字面常量，与产物无关。 |
| F017 | `kun/control_plane/productization.py:2351` | `CapabilityEvaluation` 里 `passed: True` 硬编码，`result_quality=0.92 if decision=="adopt" else 0.9`，把"外部行为对比"直通 production 能力。 |
| F008 | `kun/control_plane/game_production.py:6653-6974` | 质量 checks 是**字符串指纹存在性**（`"companionPortrait" in app`、`"questDeck" in app` …），即"源码里有没有这个标识符"，而非"功能是否真的工作"；再映射到硬编码分数。 |
| F009 | `kun/control_plane/game_production.py:2913-6026,7050-7613` | 约 60% 文件体是单一游戏项目的内嵌 TS/React 源码、SVG、CSS 与逐版本 string-replace 补丁（`_patch_app_for_product_gamefeel_v32~v55`）——一条 mission 的重放日志焊死在平台层。 |

## 为什么不在 loop 内自动改

- **不是 bug，是缺真实度量**：把硬编码 0.82 改成"真实评分"需要先定义"真实评分"怎么算（跑测试覆盖率？真实 LLM 评审？外部 playtest？），这是产品+架构决策。
- **F009 是大型拆分**：把游戏源码/补丁迁出 god-module 需配套迁移测试与 dogfood 脚本调整，单次 loop 无法安全完成。
- 盲改会让"绿"变得没有意义（正是审查批评的"自产证据"）。

## 建议方向

1. **门禁分数必须来自可追溯证据，禁止字面常量**（F016/F017）：
   - `GateEvaluation` / `CapabilityEvaluation` 的每个维度分数必须由一个 evaluator 函数产出，且 `evidence_refs` 指向真实证据（测试报告、覆盖率、外部评审记录）。
   - 加一条不变量测试：禁止 `finalize_mission` / productization 评估在无对应 evidence 时给出 pass（可用 AST/grep 守卫 + 单测断言"无证据→非 pass"）。
2. **字符串指纹 → 行为检查**（F008）：把"标识符是否出现在源码"替换为"功能是否在构建/运行期可验证"（npm test/build 退出码、关键交互的 e2e 断言）。指纹检查至多作为冒烟，不得作为 gate 主依据。
3. **拆 game_production**（F009）：按 `docs/CONTROL_PLANE_DOMAINS.md` 已有的 `kun/domains/` 方案，把游戏源码/模板/逐版本补丁迁出平台层；平台层只保留通用 runner 协议。与 [F001](F001.md) 的监督独立化、外部监督独立进程一并排期。

## 测试计划（实施时）

- 不变量：`finalize_mission` 在"工作项未全完成 / 无测试证据"时不得产出 `pass` / `ready_to_deliver`。
- 不变量：productization 评估 `passed` 必须由对比结果推导，构造无证据的输入时应得 `passed=False`。
- 拆分后：game_production 平台层不再包含具体游戏标识符（grep 守卫）。

## 影响 / 排期

- F016/F017 可作为**中等规模**改造先做（定义 evaluator + 不变量测试），风险中等但价值高（直接修复 RSI 信号真实性）。
- F008/F009 与 F001、external_supervisor 独立进程、game_production 拆分强耦合，建议作为一个"交付门禁可信化 + god-module 拆分"专项一起排期。
