# F019（high）· 设计方案：FileControlPlaneStore O(N²) 写放大 + 静默丢未知字段

> 状态：needs-design（持久层格式重设计 + 跨进程一致性，不能在单文件快照格式内一次安全改绿）
> 文件：`kun/control_plane/file_store.py`

## 问题（已核实）

1. **每次单条写入 = 全量重读 + 全量重写（O(N²)）**。`_put_and_persist`（432-446）在非事务路径下，每个 `put_*` 都：`_load_from_disk_locked()`（把整份 JSON 读回内存做跨进程合并）→ `active_bucket.put(record)` → `_persist_unlocked()`（`_snapshot_locked()` 全量序列化 + tempfile + `os.replace` 整文件落盘）。N 条记录顺序写入 ⇒ 累计 O(N²) 读写与序列化成本。`daemon` 每 tick、长任务每步都在写，文件随 mission/work_item/ledger 增长后会持续变慢。
   - 已有缓解：`transaction()`（285）在 `_transaction_depth>0` 时只入内存、退出时一次性 persist。但这要求**调用方显式包事务**，多数 `put_*` 散点调用没有。
2. **静默丢弃未知字段**。`_load_bucket`（411-430）在 `model_validate` 前用字典推导只保留 `model.model_fields` 里的键：
   ```python
   raw_record = {f: raw_record[f] for f in model.model_fields if f in raw_record}
   ```
   磁盘上存在、但当前 Pydantic 模型未声明的字段（旧/新 schema 混跑、外部写入）在 load 时被丢弃，且**无任何日志**；下次 persist 永久丢失。

## 为什么不在 loop 内自动改

- 消除 O(N²) 必须改**存储格式或刷盘策略**（单文件全量快照天然要全量重写）——属持久层重设计，含迁移与跨进程一致性风险，非一次安全编辑。
- 保留未知字段需要给域模型加 `extra="allow"` 或引入 envelope，影响面大（全部 control_plane 模型 + 序列化语义）。

## 建议方向

**A. 写放大（择一，按复杂度递增）**
1. **脏标记 + 防抖刷盘（最小侵入）**：`put_*` 只标记 dirty + 入内存，后台/退出/显式 `flush()` 时合并落盘一次；保留 `os.replace` 原子性。把 daemon 每 tick 的多次 put 自然合并为 1 次写。
2. **按 bucket 分片文件**：每类记录（missions / work_items / ledger…）独立 JSON，单次 put 只重写所在分片，O(N²)→O(N·k)。
3. **append-only 事件日志 + 周期 compaction**：写为追加，读时回放/快照；最彻底，但要做 compaction 与崩溃恢复。
   - 推荐先做 (1)：风险最低、即时缓解；(2)/(3) 视规模再上。同时把 daemon/长任务的批量写显式包进 `transaction()`。
**B. 未知字段**
- 最小：丢弃时 `log.warning("file_store.dropped_unknown_fields", key=..., dropped=[...])`，把"静默"变"可观测"。
- 进一步：对需要前向兼容的记录类型，用 `model_config = ConfigDict(extra="allow")` 或专门的 `extra: dict` 旁路字段保留未知键，persist 时回写。

## 测试计划（实施时）
- 写 N 条后断言落盘次数 = O(N)（脏标记/事务路径）而非 O(N)（每条一次）。
- round-trip：含未知字段的 JSON → load → persist → 字段保留（或至少产生 warning）。
- 跨进程：两个 store 实例交替写，最后一致（不丢更新）——与 F011/F014 并发项一并验证。
