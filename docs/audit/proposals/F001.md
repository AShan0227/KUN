# F001（critical）· 设计方案：游戏交付门禁"自批 + 覆盖人审"

> 状态：needs-design（不在 fix-loop 内自动改——涉及评审信任模型重设计，需人评审后实施）
> 相关文件：`kun/control_plane/game_production.py`、`kun/cli.py:1746-1747`

## 1. 问题（已核实的完整攻击链）

游戏交付的"外部监督 + 真人评审"门禁是**自引用**的，机器可以给自己盖章通过，并且会**覆盖人类的 fail 裁决**：

1. **同一实例兼任裁判与被裁判**：`cli.py:1746-1747` 把 `KUN_GAME_PRODUCTION_RUNNER_OWNER`（生产者）和 `EXTERNAL_SUPERVISOR_GATE_OWNER = "external-supervisor-gpt5.5"`（外部监督）注册成**同一个 `game_production_runner` 实例**。所谓"外部监督"从不调用任何外部模型或真人。
2. **自评时显式无视人审**：`game_production.py:1791-1794` 计算自评 payload 时传 `ignore_local_player_review=True`（`_final_player_experience_payload(..., ignore_local_player_review=True)`，见 6586-6621），即先把已存在的人类差评排除在外。
3. **自写"approved"文件，文件名混入人审命名空间**：自评 `pass=True` 时（1797-1845）写 `docs/player-experience-{work_item}-supervisor-review.json`，`verdict="approved_current_supervisor"`、`pass=true`、`final=true`。该文件名匹配人审扫描模式 `player-experience-*.json`（`LOCAL_PLAYER_REVIEW_PATTERNS`，132-137）。
4. **按 mtime 取最新 → 机器必然压过人类**：`_latest_local_player_review_status`（6430-6474）在所有 `player-experience-*.json` 中用 `max(..., key=mtime)` 选"最新结论"。机器的 approve 文件是在门禁运行时写的，mtime 必然晚于人类先写的 fail。`"approved"` ∈ `LOCAL_PLAYER_REVIEW_PASS_VERDICTS`，于是机器的"通过"成为"最新结论"，人类的 `"fail"`（∈ BLOCKING）被盖掉。

**影响**：这条门禁是 KUN "RSI 真闭环 / 自主交付"叙事的关键验收关卡。它可被同进程代码机械绕过、且会反转人工否决——对整个自评体系的可信度是根本性削弱（自产证据问题的最严重实例）。

## 2. 修复原则

1. **职责分离（SoD）**：监督/裁判的 owner 与生产者**不得是同一实例**；至少不得共用同一份会写 artifact 的执行体。理想态是 ADR-023 的独立进程外部监督（见 F-高 一批 external_supervisor 项）。
2. **人审优先级按"权威"而非"时间戳"**：人类/真实玩家的 blocking 裁决一旦存在，机器自评**不得覆盖**。绝不能用 mtime 决定"人 vs 机"的胜负。
3. **机器评审与人审命名空间隔离**：机器写的 review 文件不得落进人审扫描模式（`player-experience-*.json`）。换独立前缀（如 `machine-gate-*.json`），并在 `_latest_local_player_review_status` 显式排除机器来源。
4. **取消 `ignore_local_player_review`**：自评不得以"忽略人审"为前提；存在 blocking 人审时自评直接判不通过。

## 3. 建议的具体改动

- `cli.py`：`EXTERNAL_SUPERVISOR_GATE_OWNER` 不再指向 `game_production_runner`。短期：指向一个**独立的**监督 runner 实例（即便复用类，也要求其只读、不得写 `player-experience-*` 文件）；中期：接 `kun/external_supervisor` 的独立进程（与 ADR-023 落地项合并）。
- `game_production.py`：
  - 删除 `ignore_local_player_review=True` 路径；自评前先读 `_latest_local_player_review_status`，若 `allows_delivery is False` 则门禁直接 fail，不写 approve。
  - 机器 review 文件改用 `machine-gate-{work_item}-review.json` 前缀，**不**复用 `player-experience-*`。
  - `_latest_local_player_review_status`：(a) 显式跳过机器来源文件（按 schema 字段 `reviewer`/`schema` 或文件前缀判定）；(b) 决策改为"**任一** conclusive blocking 人审存在 → block"，而非"最新一条说了算"——blocking 优先于 pass，与 mtime 无关。
- 人审 schema 增加可信来源标记（如 `source: "human" | "machine"`），扫描只采信 `human`。

## 4. 测试计划

- 人审 fail 存在 + 机器自评 pass（且机器文件 mtime 更新）→ 门禁结果必须是 block。
- 机器写的 review 文件不得被 `_latest_local_player_review_status` 采信。
- 监督 owner 实例 ≠ 生产 owner 实例（注册层断言）。
- 无任何人审时，机器自评不得单独构成"final 通过"（至少标记为 provisional，需要外部确认）。

## 5. 风险 / 范围

- 改动落在 7907 行 god-module 内，且与 F-高「game_production 拆分」「external_supervisor 独立进程落地」强相关，建议三者一并排期。
- 现有 dogfood/e2e 脚本可能依赖当前"自动通过"行为（见 extra_findings 的脚本诚实度项），实施时需同步修正这些脚本的期望，避免用脚本固化漏洞行为。
